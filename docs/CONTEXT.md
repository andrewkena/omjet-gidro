# Контекст проекта и принятые решения

Документ фиксирует обсуждение, из которого появился sl2sync, чтобы продолжать работу с тем же пониманием задачи.

## Задача

Лодка на ArduRover (arduboat) выполняет промеры глубин для построения карт глубин водоёмов. Эхолот — Lowrance.
Проблема: показания глубины приходят с задержкой относительно координат, поэтому точки смещаются вдоль галса.
Например, при 2 м/с и задержке 1,5 с сдвиг составляет 3 м. На склонах это даёт заметную ошибку глубины.

## Откуда берётся задержка

1. **Обработка внутри Lowrance.** Сглаживание, Noise Rejection, фильтры поверхности, автодиапазон.
   Глубина «запаздывает» на сотни миллисекунд и больше, особенно на перепадах дна.
2. **Вывод NMEA 0183** (DPT/DBT). Обычно 4800 бод и около 1 Гц, сообщения ждут в очереди.
   Шлюз NMEA 2000 → 0183 добавляет буферизацию.
3. **Привязка в ArduPilot.** `WATER_DEPTH` берёт координату в момент *получения* глубины, а не измерения.
4. **GPS внутри Lowrance** сам запаздывает относительно реального положения.

Меры на стороне эхолота: минимизировать сглаживание и Noise Rejection, поставить максимальный Ping Speed,
выставить Keel offset = 0 (осадка учитывается в sl2sync через `--draft`).

## Выбранная схема

Онлайн-канал NMEA → ArduPilot не используется для итоговой карты. Вместо этого:

- с эхолота берётся запись **.sl2**;
- на лодке стоит отдельный **GNSS-приёмник** для точных координат (RTK/PPK);
- синхронизация и привязка выполняются в постобработке программой `sl2sync.py`.

## Формат .sl2 (как реализовано в парсере)

- Заголовок файла 8 байт (парсер проверяет также вариант 10), поле формата: 2 = sl2, 3 = sl3.
- Кадр: заголовок 144 байта, затем данные эхограммы. Поле `frame_offset` (смещение 0) равно позиции
  кадра в файле. Это используется для проверки кадров и пересинхронизации при повреждениях.
- Поля кадра (смещение, тип): `frame_size` 28 u16, `channel` 32 u16, `frame_index` 36 u32,
  `range_ft` 44 f32 (см. ниже), `unix_s` 60 u32 (см. ниже), `depth` 64 f32 (футы),
  `speed_gps` 100 f32 (узлы), `temp` 104 f32 (°C), `lon` 108 i32, `lat` 112 i32,
  `course` 120 f32 (рад), `alt` 124 f32 (футы), `heading` 128 f32 (рад), `time1` 140 u32 (мс).
- **`range_ft` (смещение 44) — окно показа (диапазон) сонара для этого пинга, футы.** Lowrance меняет
  его автоматически ступенями — на двух проверенных реальных файлах видны только значения 4/6/10/16/
  20/30 м (после перевода из футов), и `depth_ft` (глубина дна) ни разу не превышает `range_ft` (0
  нарушений на обоих файлах) — то есть это именно окно показа, а не сама глубина. Раньше это поле не
  было известно, и для растяжения столбца эхограммы под глубину пробовали использовать `depth_ft`
  (глубину дна) — предположение диапазон≈глубина оказалось неверным (диапазон ощутимо, иногда в разы,
  больше глубины) и давало на картинке ложные резкие «иглы». `range_ft` — то самое поле: байт N в
  столбце соответствует глубине `N / (число_байт_пинга) · range_m`. Используется в
  `build_echogram_image` (gui.py) для пересчёта всех столбцов к единому масштабу глубины (общий
  максимальный диапазон в записи, линейная интерполяция) — без этого при смене диапазона на картинке
  виден резкий «шов» (проверено визуально на реальном файле — до исправления заметны вертикальные
  разрывы текстуры на границах смены диапазона, после — гладкий профиль дна). Также используется в
  оценке твёрдости дна (`estimate_bottom_hardness_ping`) для перевода ширины пика из байт в метры —
  без этого резкость пика в сырых байтах была систематически «мягче» на большем диапазоне (меньше
  байт на метр) независимо от реальной твёрдости дна.
- Каналы: 0 Primary, 1 Secondary, 2 DownScan, 3/4/5 SideScan. По умолчанию берётся 0.
- **`time1` — миллисекунды от начала записи, а не абсолютное время.** Отсюда вся задача синхронизации
  глубины с треком (see below); `unix_s` даёт лишь точку отсчёта записи, а не время каждого пинга.
- **Кадр с `frame_index == 0` — служебная «заголовочная» запись канала, не настоящий пинг.** В файле
  по одному такому кадру на каждый встречающийся канал, в самом начале файла. Поле **`unix_s`**
  (смещение 60) несёт в нём настоящее unix-время начала записи (UTC, секунды) — проверено на двух
  реальных файлах (`examples/data/*.sl2`), совпадает с датой/временем в имени файла (его присваивает
  сам Lowrance) с точностью до нескольких секунд. Используется в GUI как надёжная замена mtime файла
  для начала/конца трека в сводке (`read_echogram_file`/`read_sl2` в gui.py/sl2sync.py) — mtime
  зависит от того, как файл попал на диск (копирование с карты памяти может исказить дату) и в
  реальном случае пользователя оказался ошибочным на 4 месяца. При этом сам служебный кадр не всегда
  несёт достоверные `time1`/глубину/позицию: на одном из двух проверенных файлов у него `time1` было
  равно 4294967262 мс (почти предел uint32, ≈49.7 суток) — не переполнение счётчика, а, похоже,
  служебное значение-заглушка. Смешанный с настоящими пингами, такой кадр после сортировки по
  времени улетал в конец массива и создавал гигантский ложный разрыв (длительность записи считалась
  как тысячи часов), ломая эхограмму/графики/таймлайн. `read_sl2` теперь извлекает `unix_s` из этого
  кадра и полностью исключает сам кадр из данных трека/эхограммы (теряется максимум один кадр на
  канал) — обрывов на проверенных реальных файлах после этого не остаётся.
- Координаты — Mercator Lowrance на полярном радиусе R = 6356752.3142:
  `lon = x / R · 180/π`, `lat = (2·atan(exp(y / R)) − π/2) · 180/π`.

Структура взята из общеизвестных описаний формата. Поля, перечисленные выше (включая `unix_s`),
проверены на двух реальных файлах пользователя (`examples/data/Sonar_0{1,2}_Gorodok_2026-05-26_*.sl2`)
и совпали с ожиданиями (курс/трек/дата) — остальные аспекты формата (например .sl3) по-прежнему
не проверены.

## Алгоритм sl2sync

1. Чтение sl2 и GNSS-трека (NMEA GGA+RMC/ZDA, RTKLIB .pos с переводом GPST → UTC −18 с, CSV).
2. **Грубое смещение времени** — нормированная кросс-корреляция скорости GNSS и скорости Lowrance.
   Берутся несколько лучших пиков, потому что скорость бывает квазипериодичной.
3. **Уточнение** — минимизация СКО между позициями GPS Lowrance и GNSS-треком (постоянный сдвиг
   позиций вычитается медианой). Среди пиков выбирается тот, где СКО минимально.
4. **Дрейф часов эхолота** — то же уточнение в окнах по 300 с (только окна с поворотами, на прямом галсе
   сдвиг по времени ненаблюдаем), линейная регрессия. Модель:
   `t_abs = t_rel + a + b · (t_rel − t_mid)`.
5. **Остаточная задержка глубины L** — глубина относится к позиции на момент `t_abs − L`.
   Автоподбор (`--auto-latency`): перебор L, минимизация дисперсии глубин внутри ячеек сетки.
   Работает только при встречных/пересекающихся галсах над склонами.
   Важно: смещение из п. 3 выравнивает по GPS Lowrance, который сам запаздывает, поэтому L учитывает
   разницу между запаздыванием GPS Lowrance и запаздыванием глубины и может быть любого знака.
6. **Геометрия.** Вынос датчика относительно антенны `--lever ВПЕРЁД ВПРАВО` с поворотом по курсу GNSS
   (курс удерживается при скорости < 0,3 м/с). Полная глубина = глубина sl2 + `--draft`.
   Отметка дна = высота антенны (GNSS) − `--antenna-height` − полная глубина.
7. Фильтрация выбросов скользящей медианой, фильтр по качеству GNSS (`--min-fix`).
8. Вывод: CSV точек, грид (.asc + .prj; GeoTIFF при наличии rasterio), отчёт PNG, summary.json.

## Проверка

`make_test_data.py` генерирует синтетику: 12 встречных галсов + 4 поперечных над склоном,
смещение времени, дрейф 25 ppm, задержка глубины 0,8 с, GPS Lowrance 1 Гц с запаздыванием 0,5 с и шумом,
выносы антенн, выбросы глубины.
Результат: дрейф восстановлен (около −30 ppm при истинных −25), ошибка глубины после обработки
3,3 см СКО при заложенном шуме 3 см.

## Практика в поле

- Для измерения задержки пройти туда и обратно над резким свалом дна (бровка, опора пирса).
  Расхождение бровки L на встречных галсах при скорости v даёт Δt ≈ L / (2v).
- Найденную задержку можно задавать через `--latency` для всех выходов с той же связкой и настройками.
  Смещение времени (`--offset`) у каждой записи своё.

## Формат GNSS-трека UBX (u-blox binary)

`read_ubx` в sl2sync.py читает поток UBX-сообщений (0xB5 0x62, class/id/length/
payload/checksum, 8-бит Флетчера) по эпохам (номер эпохи — поле iTOW, общее у
всех NAV-сообщений одного цикла решения). Два варианта встречаются на практике,
оба поддержаны:
- **UBX-NAV-PVT** (0x01,0x07) — всё в одном сообщении, включая RTK float/fixed
  через поле carrSoln (биты 6:7 байта flags).
- **UBX-NAV-POSLLH (0x01,0x02) + UBX-NAV-STATUS (0x01,0x03) + UBX-NAV-TIMEUTC
  (0x01,0x21)** — классический набор без NAV-PVT. Проверено на реальных файлах
  (`examples/data/{Base,Rover}_20240808*.ubx`, сырой лог для постобработки в
  RTKLIB) — там нет NAV-PVT вовсе, только эта тройка, качество фикса везде
  «одиночный» (q=1), потому что RTK не разрешён в реальном времени без потока
  поправок — это ожидаемо для сырого лога, а не баг парсера. У NAV-STATUS нет
  признака RTK float/fixed (появился только в NAV-PVT), поэтому по этой тройке
  можно определить максимум DGPS/одиночный/dead reckoning.

Для точного RTK-трека штатный путь остаётся прежним: обработать пару Base+Rover
`.ubx` через RTKLIB (`convbin`/RTKPOST) в `.pos` — прямое чтение `.ubx` в этом
проекте — быстрый способ посмотреть трек, а не замена постобработке.

## Открытые вопросы и идеи

- Проверить парсер на реальных .sl2; поддержать .sl3 (другой размер и смещения полей кадра).
- Собственный поиск дна по сырой эхограмме из sl2 — убирает внутреннее сглаживание Lowrance.
- Пакетная обработка нескольких sl2 за один выход, объединение в одну карту.
- GUI (например, PySide6) для выбора файлов и просмотра результата.
- Применить найденную задержку в онлайн-конвейере (`WATER_DEPTH` → карта): буфер позиций
  и привязка глубины к позиции на `t − Δt`.
